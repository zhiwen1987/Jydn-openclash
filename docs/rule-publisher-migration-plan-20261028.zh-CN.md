# 规则仓库拆分、发布和切换审计

> 审计基线：`Jydn-openclash` main `f83ff23ce9a9f0d59b23784440d740194d086854`，2026-10-28。
> 边界：本报告只核对仓库代码、GitHub 仓库元数据和公开发布产物；未连接路由器、管理中心或其他生产设备，未执行迁移、发布、可见性变更或生产验收。

## 结论

三个仓库应保持下列单向关系：

```text
Jydn-openclash（规则/模板唯一编辑源）
  └─ 校验、允许列表导出、单一发布工作流
       └─> Jydn-openclash-rules（唯一公开分发端）

clash-center（私有管理中心）
  └─ 只消费已发布规则/适配 OpenClash，不发布规则
```

当前代码已实现从旧仓库到公开仓库的单向允许列表发布；当前旧仓库模板仍引用该仓库的 17 个规则地址。按既有记录，生产曾使用这些地址；本次未连接生产设备，不能断言当前运行时仍有 17 项依赖。公开仓库已具备 16 个可直接替换的通用产物；`webrtc-client.yaml` 是有意保留的空占位，必须先完成现场本地规则注入，才能切换。

## 迁移与现网切换步骤

### 1. 固定单一发布方

1. 把 `Jydn-openclash` 定义为唯一编辑源，保留现有构建、校验和允许列表导出。
2. 把 `Jydn-openclash-rules` 定义为唯一公开分发端；拒绝手工直接修改，只允许专用发布凭据写 main。
3. `clash-center` 不增加规则发布工作流，也不把运行时判断回写公开仓库。
4. 禁止公开仓库反向同步到源仓库；这是避免两个仓库循环覆盖的关键约束。

### 2. 先闭合 WebRTC 现场规则

1. 在消费端建立已认证的本地 file provider，仅包含现场 WebRTC 匹配范围。
2. 确认生成后的最终配置仍在原有优先级位置引用该本地 provider，不引用公开空占位作为有效规则。
3. 用非生产样例和真实现场连接分别验证命中与不命中，证明空占位不会造成保护静默失效。

此步未完成时，不应切换整份公开模板。

### 3. 生成候选配置并做静态验证

1. 从同一源提交生成候选模板，将 16 个通用 provider 统一改为公开分发仓库对应路径。
2. 用本地已认证 provider 替换 WebRTC 占位，确保规则顺序、目标组和更新间隔不变。
3. 对候选与当前最终配置做语义 diff：除 provider 来源和 WebRTC 本地注入外，不允许出现规则、分组、DNS 或节点选择变化。
4. 确认候选配置中已无旧仓库的模板或规则读取地址。

### 4. 小范围切换与观察

1. 备份切换前最终配置、provider 缓存、规则清单和当前策略选择，并完成一次不依赖网络下载的恢复演练。
2. 只对一个候选实例切换，手动刷新所有 provider，核对条数、内容指纹、无空规则和无解析错误。
3. 验证国内直连、境外代理、拒绝、金融、开发、流媒体、通信以及 WebRTC 现场规则的新连接实际命中。
4. 至少覆盖一个最长 24 小时的规则刷新周期，再做一次强制更新与重启恢复验证。
5. 观察期内保持旧仓库公开且不变，确保可立即回退。

### 5. 全量切换和私有化门禁

1. 小范围验收通过后，全量改用已验收的公开模板/规则地址，重复更新、重启恢复和真实业务验收。
2. 全局扫描消费配置、自动化、转换任务和文档，证明不再存在旧仓库的运行时读取依赖。
3. 改可见性前，需另行授权建立一个独立私有预演仓库，或在已授权且不会触及 `clash-center` 的等价私有源条件下，真实运行一次完整发布链。预演应证明 Actions 能启动、专用写凭据仅能写隔离的公开预演目标，且产物与源提交一致。已有文档记录私有仓库 Actions 曾受账户计费/支出限额阻塞，因此这项不能用公开仓库的成功代替。本轮不新建预演仓库，不修改 `clash-center`。
4. 在上述证据全部通过、回退观察窗口结束后，才能把旧仓库改为 Private。
5. 私有化后验收：旧仓库匿名读取失败、公开仓库匿名读取成功、新的私有源提交能唯一地发布到公开仓库。

## 回滚方案

### 回滚触发条件

- 任意 provider 下载、校验或解析失败；
- 规则数量/内容指纹与切换前不一致；
- WebRTC 本地规则为空、顺序变化或真实连接未命中；
- 配置重载、重启或定时更新后无法恢复；
- 分流样本或真实业务出现新回归。

### 回滚步骤

1. 停止继续扩大切换范围，保留当时日志和最终配置作为证据。
2. 恢复切换前的整份配置和 provider 定义，而不是逐行手改；保留当前策略选择状态。
3. 从仍公开的旧仓库重新拉取 17 个规则，验证条数、指纹、解析和实际命中恢复。
4. 重做国内/境外/拒绝/业务组和 WebRTC 关键样本；确认无回归后才结束故障状态。
5. 仅在根因、修复和重新验收均有证据后，才可再次候选切换。

回退观察窗口结束前不得私有化旧仓库；这样回滚不需要临时改可见性或分发新凭据。

## 命中率、风险与需决定事项

### 改动摘要

- 本块只新增审计与迁移方案文档，没有修改任何规则、模板、发布器、工作流或生产配置。
- 公开发布结果与当前源基线的独立导出结果为 20/20 blob 相同。
- 17 个旧地址依赖全部已列出：16 个通用产物就绪，1 个现场 WebRTC 规则被隔离占位机制阻断。

### 命中率前后对比

| 指标 | 变更前 | 变更后 | 说明 |
|---|---:|---:|---|
| 生产分流命中率 | N/A | N/A | 本块没有生产切换，也未连接生产设备，不虚构命中数据 |
| 公开发布内容等价率 | 20/20 | 20/20 | 独立导出与公开 main 的 Git blob 逐个相同 |
| 旧规则依赖迁移就绪率 | 16/17 | 16/17 | 本次只审计，WebRTC 本地注入未执行 |

### 主要风险

1. **WebRTC 静默失效**：整份切换公开模板会将现场规则变成空 payload，如果没有本地注入，构建和下载可以看似成功，但规则已不起作用。
2. **发布器因私有 Actions 计费门禁停止**：当前公开源仓库发布成功，不能证明改为私有后仍可启动。
3. **两个写入方互相覆盖**：如果允许公开仓库手改、Clash Center 发布或反向同步，下一次源仓库发布会删除/覆盖这些变更。
4. **一次性切换难定位回归**：模板和 17 个 provider 同时变更时，空规则、缓存和顺序异常难以快速隔离。
5. **过早私有化破坏回滚**：旧匿名地址在还有运行时引用时会立即失效，并且回滚也需要新的认证链。

### 需要所有者决定

1. 确认 WebRTC 采用“已认证本地 file provider”方案（推荐），还是继续依赖旧公开现场规则（会持续阻塞旧仓库私有化）。
2. 确定小范围切换的维护窗口与观察期；本方案建议至少覆盖一个 24 小时刷新周期。
3. 决定是否另行授权独立私有预演仓库，并解决私有源 Actions 计费门禁；只有预演发布链真实通过，才进入旧仓库可见性变更。
4. 确定公开分发仓库的 main 保护规则，使专用发布方可写，普通人工提交不会成为第二发布方。
