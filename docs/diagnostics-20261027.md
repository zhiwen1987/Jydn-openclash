## 2. “无订阅信息”：节点数据和套餐元数据断开

活动配置为 `精准稳定-v1-r4-ha-subscription-managed.yaml`，两个公共 provider 通过 249 的受控发布地址加载。最初只读核查结果如下，不表示后续绑定仍然缺失：

| 核查项 | 结果 |
|---|---|
| 当前配置匹配的 `subscribe_info` / `config_subscribe` 信息绑定 | 未找到匹配条目 |
| 两个公共 provider HTTP 请求 | 均 200 |
| 两个响应是否含 `subscription-userinfo` | 均否 |
| 已安装 LuCI 是否支持读取该信息头及 YAML provider 回退查找 | 是 |

OpenClash 能获得节点文件，但该路径没有提供已用流量、套餐总量和到期等信息。因此截图显示“无订阅信息”，不能据此判定节点全部失效，也不能拿首页“下载总量”当供应商已用流量。

后续已按独立绑定方式处理 Provider_BFFC55：原始接口四个套餐字段有效，节点继续由 249 发布，源/运行文件、DNS、规则定义及 84 个业务/自定义选择保持不变；真实 LuCI HTTP 取数通过。没有新增公共透传接口，另一来源仍需核验并绑定。实际备份、回退及遇到的两次恢复见[实施记录](subscription-info-binding-20261027.md)，用法见[管理页面手册](management-pages.zh-CN.md)。

## 3. IPv6：已复现的是检测站看到的出口

用户观察位置为 OpenClash 首页下方的“IP 地址／访问检查”。读取的已安装实现由旁路由向各检测服务发起请求，不是整个局域网统一出口报告。

本轮证据：

- OpenClash UCI 的 IPv6 代理与 IPv6 DNS 开关均为 0；运行 YAML 的 `ipv6` 与 `dns.ipv6` 均为 false。
- 取证时旁路由没有公网 IPv6 地址。
- 按页面同类检测方式，本地强制 IPv4 请求 IP.SB 与 IPv6-only IPify，两个响应都返回 IPv6 出口，地区/ASN 与代理供应网络相符。
- 通过正常代理入口发起的另一组检测也记录到实际代理节点链；这只证明相应检测连接，不替代其他域名的规则验收。

这符合“本地 IPv4 连接代理，代理服务器通过自身 IPv6 访问目标”的链路。公开文档不固定保存生产出口完整 IP 或节点名称；复核时以新的响应与完整连接链为准。

关闭面板 IPv6 显示不会修复真实泄漏；单个 IPv6 结果也不能证明泄漏。全网验证还需检查终端 IPv6 地址与路由、IPv6 防火墙接管、DNS/DoH/DoT 路径和真实请求来源。

## 4. 节点数量：原始、候选、发布、运行分别计算

### 4.1 本轮取证样本

以下为同轮只读核对，不是供应商承诺数量或长期固定数量：

| 阶段 | 来源 A | 来源 B | 说明 |
|---|---|---|---|
| 原始缓存条目 | 56 | 24 | 包含说明项等条目 |
| 按生产规则过滤后 | 53 | 22 | 保留合法名称与基本节点结构 |
| 当前发布 | 27 | 18 | 来源 B 保留已验收的旧发布 |
| 内核运行真实节点 | 27 | 18 | 与当前发布逐来源数量一致，共 45 |

另有以下口径：

- 过滤后合计 75 条，跨来源端点唯一值为 70，重复条目 5 条；该统计不代表控制器必须跨来源统一删除重复端点。
- 当前发布清单的 `quarantined` 为 43；对未准入的新端点记录核对时，39 条为 `busy`，4 条为 `native_admission_ValueError`。
- Local_Custom 当时有一个阻断占位项，真实自建节点为 0，不能算成一个可用代理节点。
- `status=degraded` 可以与 `release_status=unchanged` 并存：内容未变，但仍有来源准入异常并保留旧节点。

因此，上游条目多、运行节点少不自动等于面板少显示。此轮运行 provider 与发布清单相符，问题集中在新端点准入没有正常推进；不能通过绕过校验把未验收端点全部发布。

### 4.2 已证实的锁异常

旁路由存在一个父进程已退出的隔离测试内核：PPID 为 1，启动目录为 `/tmp/oc-admission.*`，与生产主内核进程不同。它的 fd9 指向 `/tmp/lan-center-admission.lock`，`/proc/<该测试PID>/fdinfo/9` 仍显示排他 FLOCK。这证明仍有进程持锁，不是仅仅遗留了一个文件名。

读取 `/usr/share/openclash/lan-center-admission.sh` 可见：脚本先在 fd9 取得锁，启动后台测试内核时没有关闭子进程继承的 fd9；虽有退出清理，但测试子进程没有自己的独立寿命上限。限制外层 SSH 命令超时不能单独证明所有后代都退出。

同时，当前控制器将 `ok=false` 的准入缓存统一按 6 小时冷却，繁忙 `busy` 也被包含其中。该实例每小时抓取周期只挑 2 个待测端点，因此一个基础设施锁异常会被放大为新节点长时间无法推进。

已经证明持锁和缓存行为可以解释持续 busy；没有证明孤儿进程最初由哪次异常中断产生。4 条 ValueError 也尚未区分具体输入、解析或解析依赖原因，不应认定为 4 个节点真实不可用。

### 4.3 最小影响修复方案（未实施）

1. 备份并核验受限准入脚本、配置生成器、中心控制代码/缓存、当前发布指针与清单、运行数量及业务选择。
2. 在隔离副本测试正常退出、TERM、外层硬超时、父进程退出、锁竞争和输入错误。子进程关闭继承锁描述符，并有独立限时、身份核验及受控清理，防止继续占锁或占端口。
3. `busy` 等基础设施暂态改为延后检测，配合短重试和全局退避；真实节点失败继续冷却，不降低新节点准入标准。
4. 上线前重新核对测试进程的启动目录、父子关系和锁，只清理身份一致的遗留测试进程；不执行 killall/pkill、不停止主内核、不重启中心 DNS。
5. 小批量重新检测，按既有发布/观察/回退流程推进。核对锁未再次遗留、运行数量与清单一致、其他业务及 DNS 保持基线。

删除锁文件本身不会关闭持锁的旧文件描述符，还可能造成两套不同 inode 上的并发锁，不能作为修复办法。不要清空整个缓存、取消门禁或反复更新订阅来凑数量。
