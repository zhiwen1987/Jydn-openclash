## 本轮决策顺序

1. 从多个入口升级为进源Clash Center 唯一管理入口，原生控制 Kuma、订阅、节点和 DNS，保持轻量原生 UI。
2. 用户要求多子智能体分工，范围包括 backend、UI、DNS、Kuma、订阅生命周期、路由器事务、部署及独立验收。
3. 明确初始 DNS 内容、节点拉取 URL 和当前业务选择必须保持；统一界面可提供 DNS 编辑能力不代表本轮有权自动调整生产 DNS。
4. 识别“订阅信息可见但未接入节点发布”缺口：采用独立候选 core 检测，已准入节点才进入 Managed_Auto；N 来源新增、删除和失败均独立处理。
5. 节点不是失败一次永久淘汰：双次成功准入，三次失败后冷却一小时，自动复测；延迟健康不等于业务可用。
6. 发现生产 core 的 GLOBAL 可暴露技术候选，改为候选彻底不进生产配置。
7. 修复心跳造成 CRUD revision 变化、发布竞态、新旧状态 CAS 和数据目录覆盖镜像代码问题。
8. Kuma 原账号密码校验失败，用户授权重置指定账号；在线备份、官方 hash/CAS 更新、登录/JWT 通过，原监控/通知保持。
9. 真实协议测试发现敏感 URL 脱敏后可能覆盖原 URL，改为整条隐藏并保留原值，支持显式清空字段。
10. CoreDNS 真实测试先遇 EPERM，确认二进制文件能力需求；再遇测试无上游，补独立本地 baseline，5/5 通过。不能把测试环境问题归因为生产 DNS 故障。
11. 旧镜像 RC2 离线构建成功，但在后续修补前生成，不可当最终产物。
12. 第三家原始订阅多路径返回 Cloudflare 502；不把缓存用量当节点 payload，也不借其他来源节点冒充成功。
13. 用户最新同意“功能先加载”：允许第三家作为待恢复缺口上线功能，不允许伪造其真实接入通过。
14. 最新只读核查生产仍 0.2.0、3101 仍保留；用户转而要求资料/工作记录全部移交 GitHub。本次交接不触发部署。

## 明确非目标

没有数学意义的完美节点健康标准；不能保证八个9。不能通过放宽 HTTP 成功码、改共享节点或 DNS 让监控假绿。不能为单个业务擅改 Windows 程序。不能把所有历史其他项目凭据/数据公开。

每次变更记录日期、提交、镜像、实际操作范围、备份、回退、验收证据和未覆盖场景。没有工具/日志证据时写“未验证”，不能写“正常”。AI 阅读旧记录后先核实现状再执行。
