# 订阅更新与容器重启恢复：17 项隔离验收

验收日期：2026-10-27，北京时间。结果：17 项隔离场景通过。本文同步已完成的测试记录，不执行部署、重启或数据恢复。

后续增量：[单向信息同步](subscription-info-sync-20261027.md)已补上“转换”地址的自动读取。本文“未自动导入”的描述是本次历史测试时的边界；当前新增关系仅用于独立名称/用量清单，节点发布清单仍不互相导入。不要将两轮各自的 17 项测试混为一轮。

**结论有前提：保留正确的持久数据卷、来源清单和启动代码挂载时，隔离副本能恢复机场名称、用量缓存、完整来源清单及元数据认证。缓存恢复不等于重新联网成功。生产中心没有重启，本结果不等于整套生产容器的重启验收。**

[机器可读脱敏摘要](evidence/subscription-restore-20261027.json)记录全部场景、来源数、保护项、被测代码散列及完整私有报告的 SHA-256。私有报告、配置、凭据、测试日志和账户真实用量不上传仓库。

## 1. 实际测试范围

- 使用与生产相同的镜像，以及从生产只读复制的当前订阅启动脚本、用量采集代码和显示资源；代码散列与文档提交前的 `main`（`077f6af0`）一致。
- 运行订阅组件的真实启动入口和原有页面扩展加载路径。隔离环境只使用模拟来源、独立数据目录及测试认证，不复制真实订阅或生产数据库。
- 实际执行订阅进程重启、Docker 容器重启、删除容器后保留数据目录重建；不是只新建一个 Python 对象代替容器测试。
- 临时容器无外部网络、无对外端口，资源限制为 0.5 CPU、192 MiB 内存；没有启动第二套生产 DNS/Kuma，没有接入真实节点发布。
- 为缩短更新场景等待，将隔离采集周期设为 3 秒；缓存重启场景恢复为 600 秒。生产周期未改，不能把测试等待时间当作生产刷新保证。

首次隔离启动未达到就绪条件，不记通过。对齐测试启动器的模块路径、固定测试端口和数据路径后完成以下场景；被测生产代码未修改。

### 来源入口不自动互相导入

这 17 项中的新增、删除和完整清单恢复，针对的是 **3103 控制目录的 `subscription-sources.json`**。OpenClash“编辑配置文件订阅信息”中“转换”等 `config_subscribe` 条目属于另一入口，当前没有把其地址列表自动导入 3103 的功能。

同日后续只读采样确认：“转换”已保存 3 条地址，3103 启用清单仍为 2 条，前两条逐项匹配，第三条未进入 3103；当前运行的受管配置读取 3103 汇总，而不是直接使用“转换”的列表。因此显示两家不代表 N 来源容量失效，也不能说两个入口已经自动同步。该数量是当次观测，后续以实际清单为准。

本次没有补录第三条、切换运行配置或修改任何订阅地址。若要联动两个入口，需另行实施并验收来源同步，不能用本轮持久恢复结果替代该功能的验证。

## 3. 自动恢复需要保留什么

以下是容器内路径。当前站点 `/data` 对应宿主机控制目录 `/root/dpanel/compose/lan-center/data/failover/`；其他站点以实际挂载为准。

| 文件或条件 | 用途 | 丢失或改变后的边界 |
|---|---|---|
| `/data/subscription-sources.json` | 来源 ID、订阅地址、启停等完整清单 | 只剩用量缓存不能还原完整私密来源配置；须从可信备份恢复 |
| `/data/subscription-usage/cache.json` | 已识别名称、套餐值、最后成功时间与退避信息 | 可在上游可用时重取；上游也不可用则无法凭空恢复 |
| `/data/subscription-usage/provider-token` | 中心与 OpenClash 元数据接口的认证 | 保留时无须重新绑定；丢失或轮换后不能承诺旧认证仍有效 |
| `/data/subscription-usage/code/` 下的现有扩展文件 | 本站点持久化的用量模块和资源 | 丢挂载、删代码或换成不兼容版本，不能按普通重启解释 |
| 原订阅启动脚本的挂载及加载路径 | 启动订阅服务并加载扩展 | 只保留镜像、改了启动入口或漏掉脚本挂载，不属于本次通过的条件 |
| 有效上游响应 | 提供新名称、用量与到期 | 上游未提供、限流、超时或凭据失效时，只能按实际状态和缓存显示 |

保留数据卷并不只是保留 `cache.json`。重建容器时应沿用经确认的数据映射、代码映射和启动参数；本文不提供覆盖当前生产 Compose 或重启生产中心的快捷命令。

## 4. 怎样判断是真正恢复还是只读到缓存

- 先看 3103 和 OpenClash 用量卡片的来源数量，再看各来源状态与“最后成功”时间；节点数不等于订阅来源数。
- 重启后读取的是有效期内的成功缓存时，卡片可能仍显示“正常”；这不证明本次已经访问上游。测试特意确认离线重启没有把最后成功时间改成重启时间。
- 新请求失败后，有历史成功值的来源显示缓存及时间；没有历史的来源显示未获取。超过有效期的旧值应按过期提示理解，不当成实时账单。
- 生产正常用量约 600 秒更新一次，页面约 30 秒刷新；失败按各来源独立退避，429 还可能延后。上游刚恢复时不保证下一秒就完成所有来源取数。
- 上游没有名称或套餐字段时，不能从节点数量、域名或内核运行流量推算真实账单。手工显示名可以覆盖名称，不能生成不存在的用量。

| 当前条件 | 可以期待的结果 |
|---|---|
| 来源清单、缓存、认证和挂载都保留 | 自动恢复历史名称和用量；新数据随后按计划获取 |
| 缓存坏了，上游可用且提供有效字段 | 自动重取名称和用量 |
| 缓存坏了，上游离线 | 清单仍在，但名称/用量未获取；待上游恢复后重试 |
| 来源配置或整个持久卷丢失 | 需要先核对并恢复备份，不能把空目录初始化当成订阅已恢复 |
| 更换镜像、启动脚本、挂载或认证 | 需要重新核验兼容性与对接，不直接套用普通重启结果 |

## 5. 日常检查与恢复边界

1. 信息显示异常时，先只读查看 3103 的来源数、每家状态和最后成功时间，不先重启 OpenClash、DNS 或整个中心。
2. 有缓存且清单完整时，区分旧值、上游失败与计划退避；只刷新页面不会强制所有供应商立即取数。
3. 少来源或出现空清单时，先核对真实数据挂载和来源文件。不要把新建空配置覆盖到原数据目录。
4. 涉及备份恢复或改挂载时，先核对目标、版本和后续人工编辑，再安排授权维护。代码回退与完整数据卷恢复是不同操作。

最新名称修正的备份及受控代码回退见[名称与 N 来源验收记录](subscription-usage-names-acceptance-20261027.md#最新备份与恢复)。其中命令用于撤销对应代码事务，不能当成整个数据卷丢失后的完整恢复。更早事务的撤销顺序见该页及[自动用量显示记录](subscription-usage-auto-20261027.md)。

本轮没有新的生产代码部署或恢复事务；测试容器及测试守卫已清理。17 项验收当次前后核对：生产文件、规则定义、84 个业务选择、核心 PID、生产容器身份/启动时间及 DNS/Kuma 进程均未变，CoreDNS 配置与此前确认基线一致。该记录是当次采样，本次文档同步没有重新执行生产重启或恢复操作。
